### 내용
1. `V5__enrollment_employee_index.sql`: 설계명세 3장의 SQL을 그대로 쓴다. 첫 줄 주석은 `-- 내 신청 내역 조회 (FR-07)`이다
2. `MyEnrollmentRow`: `public final class`. 필드는 `Long id`, `Long sessionId`, `String courseTitle`, `LocalDate startDate`, `String place`, `EnrollmentStatus status`, `LocalDateTime createdAt`, `Long precedingWaiting`. 이 순서의 public 생성자와 getter를 둔다. Javadoc: `/** 내 신청 내역 조회 결과 한 행. precedingWaiting은 같은 회차에서 나보다 앞선 대기 수다 (FR-07, D-04). */`
3. `EnrollmentRepository`에 메서드를 추가한다
   - `@Query`에 설계명세 3장의 JPQL을 그대로 쓴다. enum 상수는 전체 이름으로 쓴다
   - `List<MyEnrollmentRow> findMyEnrollments(@Param("employeeId") Long employeeId, @Param("status") EnrollmentStatus status);`
   - Javadoc에 "status가 null이면 전체. 대기 순번 정렬은 D-04"라고 적는다

### 테스트 (`EnrollmentRepositoryTest`에 추가. 기존 설정 `@DataJpaTest`, `replace = NONE`, `pgtest`를 따르고, 저장 뒤 `em.flush()`·`em.clear()`)
- 클래스의 `@DataJpaTest`에 `properties = "spring.jpa.properties.hibernate.generate_statistics=true"`를 추가한다
- 준비: 과정 1개, 회차 A·B. `created_at`은 `Enrollment.create`가 `now()`로 정하므로, 순서·동률 검증에는 `ReflectionTestUtils.setField(e, "createdAt", ...)`로 시각을 정한다
- 시나리오
  - `findMyEnrollments_returnsOnlyMine()`: 임직원 1과 2의 신청을 섞어 저장한다 → 1의 것만 나온다
  - `findMyEnrollments_filtersByStatus()`: `WAITING`, `CONFIRMED`, `null`(전체) 세 경우
  - `findMyEnrollments_ordersByCreatedAtDesc()`: 최근 신청이 앞에 온다
  - `findMyEnrollments_precedingWaitingCountsSameSessionOnly()`: 회차 A에 대기 3명(임직원 11, 12, 1 순서), 회차 B에 대기 2명을 저장한다. 임직원 1의 A 행의 `precedingWaiting`은 2다
  - `findMyEnrollments_sameCreatedAt_tieBreaksById()`: 같은 시각의 대기 2명 중 id가 큰 쪽의 `precedingWaiting`이 1이다
  - `findMyEnrollments_confirmedNotCountedAsWaiting()`: 앞선 확정 신청은 세지 않는다
  - `findMyEnrollments_executesSingleSql()`: 신청 3건(서로 다른 회차·과정)을 저장하고 `em.flush()`·`em.clear()` 뒤에 `Statistics`를 `clear()`한다. 조회 후 `getPrepareStatementCount()`가 1이다. `Statistics`는 `em.getEntityManagerFactory().unwrap(SessionFactory.class).getStatistics()`로 얻는다

### 내용
1. `MyEnrollmentResponse` (`EnrollmentResponse` 형식: `final` 클래스, private final 필드, private 생성자, getter)
   - 필드: 설계명세 2장의 표 순서대로. `waitingNumber`는 `Integer`다

2. `MyEnrollmentQueryService`
   - `@Service @RequiredArgsConstructor @Transactional(readOnly = true)` (클래스 단위)
   - 클래스 Javadoc: "내 신청 내역 조회 (FR-07, D-04). 규칙: 로그인한 임직원의 신청만 최근 신청순으로 돌려준다. 상태를 주면 그 상태만 돌려준다. 대기 순번은 저장하지 않고 같은 회차의 대기 신청 사이에서 신청 일시, 같으면 id 순으로 계산한다. 과정·회차·대기 순번은 쿼리 하나로 가져온다."

## T3. Controller + OpenAPI

### 변경 파일
| 구분 | 파일 |
|---|---|
| 수정 | `src/main/java/com/example/eduhub/enrollment/controller/EnrollmentController.java` |

### 내용
1. 경로 처리 (설계명세 5장): 클래스의 `@RequestMapping("/api/v1/sessions")`를 지우고 기존 신청 메서드를 `@PostMapping("/api/v1/sessions/{sessionId}/enrollments")`로 바꾼다. 기존 신청 테스트가 그대로 통과해야 한다
2. `@Tag` description을 `"수강 신청·내 신청 내역"`으로 바꾼다
3. 의존에 `MyEnrollmentQueryService myEnrollmentQueryService`를 추가한다
4. 메서드
   ```java
   @GetMapping("/api/me/enrollments")
   public List<MyEnrollmentResponse> myEnrollments(
       @AuthenticationPrincipal Jwt jwt,
       @Parameter(description = "신청 상태. 생략하면 전체") @RequestParam(required = false)
           EnrollmentStatus status) {
     return myEnrollmentQueryService.findMine(CurrentUser.from(jwt).getEmployeeId(), status);
   }
   ```
   - `Jwt` 파라미터에는 NFR-03의 기존 신청 메서드와 같은 방식(`@Parameter(hidden = true)` 여부 등)을 따른다
5. OpenAPI
   - `@Operation(summary = "내 신청 내역 조회 (최근 신청순, 대기 순번 포함)")`
   - `@ApiResponse`: `200` 조회 성공 / `400` 상태 값 형식 오류 (INVALID_REQUEST) / `401` 인증 필요 (NFR-03 code). 에러에는 `content = @Content(schema = @Schema(implementation = ErrorResponse.class))`

### 테스트 (`@WebMvcTest(EnrollmentController.class)`. 인증 설정과 JWT 준비는 NFR-03이 기존 신청 테스트에 쓴 방식을 그대로 따른다. `@MockBean`에 `MyEnrollmentQueryService`를 추가)
- `myEnrollments_returns200WithFields()`: `$[0].courseTitle`, `$[0].waitingNumber`, `$[0].status`
- `myEnrollments_usesEmployeeIdFromJwt()`: JWT의 임직원 ID 7 → `findMine(7L, null)` (`ArgumentCaptor` 또는 `verify`)
- `myEnrollments_withStatus_passesStatus()`: `?status=WAITING` → `findMine(7L, WAITING)`
- `myEnrollments_invalidStatus_returns400()`: `?status=FOO` → 400 `INVALID_REQUEST`, 서비스 호출 없음
- `myEnrollments_noToken_returns401()`: 서비스 호출 없음
- `myEnrollments_ignoresEmployeeIdQueryParam()`: `?employeeId=99`를 붙여도 `findMine(7L, null)`

## 위험 영역 (reviewer와 critical-reviewer가 중점적으로 본다)
1. **인가:** 임직원 ID가 JWT에서만 오는가. 요청 파라미터·헤더로 남의 내역을 볼 길이 없는가
2. **대기 순번 정확성:** 같은 회차, `WAITING`만, D-04 정렬(동률은 id)인가. 다른 회차·확정 신청이 섞이지 않는가
3. **SQL 1개:** 지연 로딩이나 추가 조회가 없는가. 테스트가 실제로 SQL 수를 세는가
4. **H2와 PostgreSQL 차이:** `:status is null` 바인딩과 select 절 서브쿼리가 두 DB에서 동작하는가
5. **기존 API 경로:** 클래스 매핑을 옮긴 뒤에도 `POST /api/v1/sessions/{id}/enrollments`가 그대로인가
6. **Flyway 번호:** NFR-03(V4), FR-08과 겹치지 않는가
