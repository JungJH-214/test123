## T1. 응답 DTO와 서비스의 순번 계산 + 단위 테스트

### 변경 파일
| 구분 | 파일 |
|---|---|
| 수정 | `src/main/java/com/example/eduhub/enrollment/dto/EnrollmentResponse.java` |

| 추가 | `src/test/java/com/example/eduhub/enrollment/dto/EnrollmentResponseTest.java` |

### 내용
1. `EnrollmentResponse`
   - 필드 `private final Integer waitingNumber;`와 `getWaitingNumber()`를 추가한다. 생성자 인자 끝에 추가한다
   - 필드에 `@Schema(description = "대기 순번. WAITING일 때만 값이 있고(1부터), 신청 시점 기준이다", nullable = true)`를 단다 (`io.swagger.v3.oas.annotations.media.Schema`)
   - `from(Enrollment)`: 기존 그대로, `waitingNumber = null`
   - 새 팩토리 `public static EnrollmentResponse waiting(Enrollment enrollment, int waitingNumber)`
     - `enrollment.getStatus() != EnrollmentStatus.WAITING`이면 `IllegalArgumentException("대기 신청에만 순번을 붙입니다")`
     - `waitingNumber < 1`이면 `IllegalArgumentException("대기 순번은 1부터입니다")`
   - 클래스 Javadoc을 "수강 신청 결과 (FR-04, FR-05)"로 바꾼다
2. `EnrollmentCommandService`
   - `decideStatus(CourseSession)`를 `decide(CourseSession)`로 바꾸고, private static final 내부 클래스 `Decision`(필드 `EnrollmentStatus status`, `long waitingBefore`)을 돌려준다
     - 확정이면 `new Decision(CONFIRMED, 0)`
     - 대기면 `new Decision(WAITING, waiting)` (이미 센 `waiting` 값을 그대로 넣는다. 다시 집계하지 않는다)
     - 대기까지 차면 기존처럼 `SessionFullException`
   - `enroll()`의 마지막: `decision.status == WAITING`이면 `EnrollmentResponse.waiting(saved, Math.toIntExact(decision.waitingBefore + 1))`, 아니면 `EnrollmentResponse.from(saved)`
   - 락 조회, 중복 확인, `save()`의 순서와 트랜잭션 경계는 바꾸지 않는다
   - 클래스 Javadoc 규칙 단락 끝에 한 문장 추가: "대기 순번(FR-05, D-04)은 락 안에서 센 기존 대기 수 + 1이다. 같은 회차 신청이 락으로 직렬화되어 새 대기가 항상 D-04 순서의 맨 뒤이기 때문이다."
3. 테스트 `EnrollmentCommandServiceTest` (설계 5절 S1~S4)
   - `enroll_seatAvailable_confirmed`: 기존 단언에 `assertThat(response.getWaitingNumber()).isNull()` 추가 (S1)
   - 추가 `enroll_capacityFullNoWaiting_waitingNumberOne`: `givenCounts(10, 0)` → `WAITING`, `waitingNumber == 1` (S2)
   - `enroll_capacityFull_waiting`(기존, `givenCounts(10, 4)`): `waitingNumber == 5` 단언 추가 (S3)
   - `enroll_capacityAndWaitingFull_throwsSessionFull`: 그대로, `verify(enrollmentRepository, never()).saveAndFlush(any())`가 없으면 추가 (S4)
4. 테스트 `EnrollmentResponseTest` (단위, 엔티티는 `Enrollment.create(...)`로 만든다. `CourseSession`은 테스트에 있는 생성 방식을 따른다)
   - `waiting_confirmedEnrollment_throws`, `waiting_zero_throws`, `from_waitingNumberNull`

### 내용

2. `EnrollmentControllerTest` (설계 C1, C2)
   - `enroll_waiting_returns201WithWaiting`(기존): 서비스 목이 `EnrollmentResponse.waiting(..., 3)`을 돌려주게 하고 `jsonPath("$.waitingNumber").value(3)` 추가 (C1)
   - `enroll_returns201`(기존, 확정): `jsonPath("$", hasKey("waitingNumber"))`와 `jsonPath("$.waitingNumber").isEmpty()` 추가 (C2. 필드를 생략하지 않고 null로 내보내는지 확인. MockMvc의 `exists()`·`value(nullValue())`는 값이 null이면 "No value at JSON path"로 실패해서 이 방식을 쓴다)
3. `EnrollmentConcurrencyTest` (pgtest, 설계 R1~R3)
   - `runConcurrently`가 성공 응답을 `ConcurrentLinkedQueue<EnrollmentResponse>`에 모으고 `Result`에 `List<EnrollmentResponse> responses`를 추가한다
   - R1 `hundredApplicants_capacityTen_confirmedTenWaitingFive`: 기존 단언 + `WAITING` 응답의 `waitingNumber` 집합이 정확히 `{1,2,3,4,5}`이고 개수 5, `CONFIRMED` 응답은 모두 `waitingNumber == null`
   - R2 `nineConfirmed_hundredApplicants_lastSeatOnlyOnce`: 기존 단언 + 대기 응답 순번이 `{1..5}`
   - R3 추가 메서드 또는 R1 안에서: DB에서 해당 회차 `WAITING` 신청을 `created_at, id` 오름차순으로 읽은 id 순서가, 응답을 `waitingNumber` 오름차순으로 정렬한 id 순서와 같다. 조회는 테스트 안에서 `EntityManager` JPQL(`select e from Enrollment e where e.session.id = :sid and e.status = :st order by e.createdAt, e.id`)로 한다. Repository에 메서드를 추가하지 않는다

## 위험 영역
- **락 밖 계산 금지:** 순번은 `decide()`가 락 안에서 센 값으로만 만든다. 저장 후 다시 세거나 별도 트랜잭션에서 계산하면 동시 신청의 순번이 겹친다. reviewer는 이것을 반드시 본다
- **응답 호환:** 필드 추가만 한다. 기존 필드 이름·타입·상태 코드를 바꾸지 않는다. `from()`의 기존 호출부는 그대로 동작해야 한다
- **FR-07과의 충돌:** FR-07(`feature/fr-07-my-enrollments-api`)이 `EnrollmentRepository`, `EnrollmentControllerTest`, Flyway V5를 건드린다. FR-05는 Repository와 Flyway를 건드리지 않는다. 먼저 병합된 쪽 위로 rebase하고, `EnrollmentControllerTest` 충돌은 양쪽 테스트를 모두 남긴다
- **인증 파라미터 숨김:** `@Parameter(hidden = true)`는 문서에만 영향을 준다. `@AuthenticationPrincipal` 주입이 그대로인지 기존 `SecurityIntegrationTest`(신청자 = 토큰 사원)로 확인한다
