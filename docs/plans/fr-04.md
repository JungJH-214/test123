### 내용
1. 예외 (`SessionClosedException` 형식)

2. `EnrollmentResponse` (`SessionResponse` 형식: `final` 클래스, private final 필드, private 생성자, getter)
   - 필드: `Long id`, `Long sessionId`, `Long employeeId`, `EnrollmentStatus status`, `LocalDateTime createdAt`
   - `public static EnrollmentResponse from(Enrollment enrollment)`. `sessionId`는 `enrollment.getSession().getId()`로 얻는다
3. `EnrollmentCommandService`
   - `@Service @RequiredArgsConstructor @Transactional` (클래스 단위)
   - 의존: `CourseSessionRepository courseSessionRepository`, `EnrollmentRepository enrollmentRepository`
   - 클래스 Javadoc (업무 규칙 한 단락): "수강 신청 (FR-04, NFR-01, D-02). 규칙: 회차 행에 쓰기 락을 걸고 확정 수를 센 뒤 저장까지 한 트랜잭션에서 한다. 확정 수가 정원보다 적으면 확정, 정원이 찼으면 대기(정원의 50% 내림까지), 대기도 차면 409 SESSION_FULL이다. 같은 회차에 이미 신청했으면 409 ENROLLMENT_DUPLICATE다. 종료된 회차는 409 SESSION_CLOSED, 없는 회차는 404 SESSION_NOT_FOUND다. 시작일이 지난 회차도 막지 않는다."
   - `public EnrollmentResponse enroll(Long sessionId, Long employeeId)`. 아래 순서를 바꾸지 않는다.
     1. `CourseSession session = courseSessionRepository.findByIdForUpdate(sessionId).orElseThrow(() -> new SessionNotFoundException(sessionId));` (`findById`나 `Optional.get()`을 쓰지 않는다)
     2. `if (session.isClosed()) throw new SessionClosedException(sessionId);`
     3. `if (enrollmentRepository.existsBySessionIdAndEmployeeId(sessionId, employeeId)) throw new DuplicateEnrollmentException(sessionId, employeeId);`
     4. `EnrollmentStatus status = decideStatus(session);`
     5. `Enrollment saved = save(Enrollment.create(session, employeeId, status), sessionId, employeeId);`
     6. `return EnrollmentResponse.from(saved);`
   - `private EnrollmentStatus decideStatus(CourseSession session)`
     - `long confirmed = countBySessionIdAndStatus(id, CONFIRMED)`. `confirmed < capacity`이면 `CONFIRMED`
     - `long waiting = countBySessionIdAndStatus(id, WAITING)`. `waiting < capacity / 2`(int 나눗셈)이면 `WAITING`
     - 아니면 `throw new SessionFullException(id)`
   - `private Enrollment save(Enrollment enrollment, Long sessionId, Long employeeId)`
     - `try { return enrollmentRepository.saveAndFlush(enrollment); }`
     - `catch (DataIntegrityViolationException e) { if (isActiveUniqueViolation(e)) throw new DuplicateEnrollmentException(sessionId, employeeId); throw e; }`
   - 판정은 `enrollment/repository/EnrollmentConstraints.isActiveUniqueViolation(e)`가 한다 (최종 검토 경고 2로 추가).
     - 상수는 `ACTIVE_UNIQUE_INDEX = "ux_enrollment_session_employee_active"`이다.
     - cause 체인을 따라간다. Hibernate 제약 이름이 있으면 상수와 같은지(대소문자 무시)로 판정한다.
     - 이름이 없으면 `SQLException.getSQLState()`가 `23505`인지로 판정한다. PG 메시지 로캘에 영향받지 않게 하려는 것이다.
     - 테스트: `EnrollmentConstraintsTest`(단위)와 `EnrollmentRepositoryTest`(pgtest, 실제 PG 예외로 참인지 확인)

### 설계명세와 다른 점 (개발자 승인, 설계명세에도 반영함)
`MISSING_EMPLOYEE_ID`는 수강 신청에만 해당하는 code다. 그래서 공통 `GlobalExceptionHandler`가 아니라 enrollment 전용 핸들러가 처리한다. 이렇게 하면 `common`이 도메인을 몰라도 된다.

### 내용
1. `EnrollmentController` (`CourseAdminController` 형식)
   - `@Tag(name = "Enrollment", description = "수강 신청")`, `@RestController`, `@RequestMapping("/api/v1/sessions")`, `@RequiredArgsConstructor`
   - 상수: `static final String EMPLOYEE_ID_HEADER = "X-Employee-Id";`
   - 클래스 Javadoc에 아래 TODO를 둔다.
     `TODO(NFR-03): 인증이 아직 없어 신청자를 X-Employee-Id 헤더로 받는다. 인증을 넣으면 로그인 사용자에서 employeeId를 꺼내고 이 헤더를 지운다.`
   - 메서드
     ```java
     @PostMapping("/{sessionId}/enrollments")
     @ResponseStatus(HttpStatus.CREATED)
     public EnrollmentResponse enroll(
         @PathVariable Long sessionId,
         @Parameter(description = "신청자 임직원 ID (임시, NFR-03 전까지)", required = true)
             @RequestHeader(EMPLOYEE_ID_HEADER) Long employeeId) {

     }
     ```
     - `@RequestBody`는 두지 않는다.
   - OpenAPI
     - `@Operation(summary = "수강 신청 (정원 안이면 확정, 정원이 차면 대기)")`

       - `201` 신청 성공 (status: CONFIRMED 또는 WAITING)
       - `400` 신청자 헤더 없음 또는 형식 오류 (MISSING_EMPLOYEE_ID), 경로 값 형식 오류 (INVALID_REQUEST)
       - `404` 회차가 없음 (SESSION_NOT_FOUND)
       - `409` 종료된 회차, 중복 신청, 정원·대기 마감 (SESSION_CLOSED, ENROLLMENT_DUPLICATE, SESSION_FULL)

## T5. 동시성 테스트 (작성만, 실행은 개발자)

### 변경 파일
| 구분 | 파일 |

| 추가 | `src/test/java/com/example/eduhub/enrollment/EnrollmentConcurrencyTest.java` |

### 내용
- `@SpringBootTest`, `@ActiveProfiles("pgtest")`. 클래스와 메서드에 `@Transactional`을 붙이지 않는다.
- 주입: `EnrollmentCommandService`, `EnrollmentRepository`, `CourseRepository`, `CourseSessionRepository`
- 상수: `THREADS = 32`, `APPLICANTS = 100`, `CAPACITY = 10`
- `@AfterEach cleanUp()`: `enrollmentRepository.deleteAllInBatch()`, `courseSessionRepository.deleteAllInBatch()`, `courseRepository.deleteAllInBatch()` 순서로 지운다
- 도우미 `private Result runConcurrently(Long sessionId, long firstEmployeeId)`
  - `ExecutorService pool = Executors.newFixedThreadPool(THREADS)`, `CountDownLatch ready = new CountDownLatch(APPLICANTS)`, `CountDownLatch start = new CountDownLatch(1)`, `CountDownLatch done = new CountDownLatch(APPLICANTS)`
  - 각 작업은 `ready.countDown(); start.await();` 뒤에 `enroll(sessionId, firstEmployeeId + i)`를 호출한다. 결과는 성공, `SessionFullException`, 그 밖의 예외로 나눠 `AtomicInteger`에 센다. 그 밖의 예외는 `ConcurrentLinkedQueue<Throwable>`에도 담는다. `finally`에서 `done.countDown()`
  - 스레드가 32개뿐이므로 `ready.await()`는 쓰지 않는다. 작업을 모두 제출한 뒤 `start.countDown()`을 하고, `done.await(60, TimeUnit.SECONDS)`가 참인지 확인한다. 마지막에 `pool.shutdown()`
  - 반환: 성공 수, 마감 거절 수, 그 밖의 예외 목록 (테스트 안 private static 클래스 `Result`)
- 테스트 ①: `hundredApplicants_capacityTen_confirmedTenWaitingFive()`

## 위험 영역 (reviewer와 critical-reviewer가 중점적으로 본다)
1. **락 경로:** `enroll()`이 `findByIdForUpdate`를 쓰는가. `findById`로 바뀌면 NFR-01이 깨진다.
2. **트랜잭션 경계:** 락 조회, 확정·대기 수 집계, `saveAndFlush`가 같은 `@Transactional` 메서드 안에 있는가. 내부 메서드 호출이나 `REQUIRES_NEW`로 쪼개지 않았는가.
3. **H2와 PostgreSQL 차이:** 부분 유일 인덱스는 H2에 없다. 중복·락 검증은 pgtest 테스트로만 확인된다. `{vendor}` 폴더 이름(`h2`, `postgresql`)이 맞아야 Flyway가 V3를 찾는다. DB별 폴더는 `db/migration` 밖(`db/vendor`)에 둔다. Flyway가 `db/migration`을 하위 폴더까지 읽어 V3가 중복되기 때문이다.
4. **무결성 위반 변환:** 제약 이름으로 거른다. 다른 무결성 위반(FK 등)을 409로 감추지 않는다.
5. **커넥션 풀:** 동시성 테스트는 Hikari 기본 풀 10개로 32개 스레드를 받는다. 락 대기와 커넥션 대기가 겹쳐 느릴 수 있어 60초를 기다린다.
6. **남은 자리 표시:** `SessionResponse.remainingSeats`는 아직 정원과 같다. FR-04 뒤에는 실제와 달라지지만, course → enrollment 의존이 금지되어 있어 이 작업에서는 고치지 않는다. 별도 작업으로 남긴다.
