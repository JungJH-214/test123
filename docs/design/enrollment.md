- 상태: 승인됨. 구현 중 바뀐 점(Flyway 폴더 위치, 400 처리 위치, 중복 판정 방식)까지 반영함
- 범위: 회차 수강 신청 API와 동시 신청 정원 보장
- 범위 밖: FR-05 대기 순번 부여(계산과 응답), FR-06 취소와 대기 승급, FR-07 내 신청 조회, NFR-03 인증

## 2. API

### POST `/api/v1/sessions/{sessionId}/enrollments` — 수강 신청
- **신청자:** 요청 본문으로 받지 않는다. 본문은 없다.
  - 임시로 요청 헤더 `X-Employee-Id`(Long, 필수)에서 읽는다 (Q3)
  - `TODO(NFR-03)`: 인증을 넣으면 로그인 사용자에서 꺼내고, 이 헤더는 지운다
- **성공:** `201 Created`, 본문은 `EnrollmentResponse`
- **판정:** 확정(`CONFIRMED`) 수가 정원보다 적으면 `CONFIRMED`다. 정원이 찼고 대기 수가 `capacity / 2`보다 적으면 `WAITING`이다. 둘 다 201이고, 결과는 `status`로 구분한다. 대기까지 차면 409 `SESSION_FULL`이고 저장하지 않는다.
- **시작일:** 시작일이 지난 회차도 막지 않는다 (Q4. 요구사항에 규칙이 없고, FR-03도 지난 시작일을 허용).

`EnrollmentResponse` (DTO, 엔티티를 반환하지 않음)
| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | Long | 신청 ID |
| `sessionId` | Long | 회차 ID |
| `employeeId` | Long | 신청자 임직원 ID |
| `status` | String(enum) | `CONFIRMED` 또는 `WAITING` |
| `createdAt` | LocalDateTime | 신청 시각 |

대기 순번(`waitingNumber`)은 FR-05에서 이 응답에 필드를 추가한다.

### 오류 코드
공통 형식은 기존 `ErrorResponse { code, message }`를 쓴다.

| HTTP | code | 조건 | 발생 위치 |
|---|---|---|---|
| 400 | `MISSING_EMPLOYEE_ID` | `X-Employee-Id` 헤더가 없거나 숫자가 아님 | enrollment 전용 `EnrollmentExceptionHandler`(`@RestControllerAdvice(assignableTypes = EnrollmentController.class)`)가 `MissingRequestHeaderException`과, 이름이 `X-Employee-Id`인 `MethodArgumentTypeMismatchException`을 처리한다. `common/GlobalExceptionHandler`는 바꾸지 않는다 |
| 400 | `INVALID_REQUEST` | 경로 값 형식 오류 (예: `/sessions/abc/enrollments`) | 같은 `EnrollmentExceptionHandler`. 헤더가 아닌 `MethodArgumentTypeMismatchException`을 처리한다 |
| 404 | `SESSION_NOT_FOUND` | 회차가 없음 | 기존 `SessionNotFoundException` 재사용 |
| 409 | `SESSION_CLOSED` | 종료된 회차 (과정을 종료하면 회차도 종료되므로 과정 종료도 여기에 포함) | 기존 `SessionClosedException` 재사용 |
| 409 | `ENROLLMENT_DUPLICATE` | 같은 회차에 취소되지 않은 신청이 이미 있음 | 새 `DuplicateEnrollmentException extends ConflictException` |
| 409 | `SESSION_FULL` | 정원과 대기(정원의 50%)가 모두 참 (D-02) | 새 `SessionFullException extends ConflictException` (enrollment/exception) |

## 3. 스키마 변경

### Flyway 번호
- 기존: `db/migration/V1__create_course.sql` 하나뿐이다. 새 번호는 **V2**, **V3**이고 겹치지 않는다.
- **H2 제약:** test 프로필(H2)도 Flyway를 실행한다. H2는 부분 인덱스(`CREATE INDEX ... WHERE`)를 지원하지 않아, 공통 폴더에 두면 `@SpringBootTest`(H2)가 모두 깨진다. → 질문 Q2
  - 결정(Q2): `application.yml`의 `spring.flyway.locations`를 `classpath:db/migration,classpath:db/vendor/{vendor}`로 바꾸고, 부분 유일 인덱스만 DB별 폴더에 둔다.

| 파일 | 내용 |
|---|---|
| `db/migration/V2__create_enrollment.sql` | `enrollment` 테이블과 일반 인덱스 (H2, PostgreSQL 공통) |
| `db/vendor/postgresql/V3__enrollment_active_unique.sql` | 부분 유일 인덱스 |
| `db/vendor/h2/V3__enrollment_active_unique.sql` | H2용 대체본. 부분 인덱스가 없으므로 아무것도 만들지 않고 주석만 둔다. 중복 방지 검증은 pgtest에서 한다 |

### V2: `enrollment` 테이블
```sql
CREATE TABLE enrollment (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    session_id  BIGINT      NOT NULL REFERENCES course_session (id),
    employee_id BIGINT      NOT NULL,
    status      VARCHAR(20) NOT NULL,
    created_at  TIMESTAMP   NOT NULL
);

CREATE INDEX idx_enrollment_session_status ON enrollment (session_id, status);
```
- `employee_id`에는 FK가 없다. 임직원 테이블이 아직 없다(NFR-03에서 정한다).
- `idx_enrollment_session_status`는 FK 인덱스를 겸하고, 확정 수 집계(`session_id`, `status`)에 쓰인다.

### V3: 부분 유일 인덱스 (PostgreSQL)
```sql
CREATE UNIQUE INDEX ux_enrollment_session_employee_active
    ON enrollment (session_id, employee_id)
    WHERE status <> 'CANCELLED';
```
- 취소(`CANCELLED`, FR-06에서 추가)된 신청은 제외한다. 그래서 취소한 뒤 다시 신청할 수 있다. 수료 등 나머지 상태는 모두 중복으로 본다.

### 엔티티 `enrollment/domain/Enrollment`
- 필드: `id`, `session`(`@ManyToOne(fetch = LAZY, optional = false)` → `CourseSession`), `employeeId`(Long), `status`(`@Enumerated(STRING)`), `createdAt`(LocalDateTime)
- 생성: `Enrollment.create(CourseSession session, Long employeeId, EnrollmentStatus status)`가 `createdAt`을 현재 시각으로 정한다. `@Setter`는 쓰지 않는다.
- `EnrollmentStatus`: `CONFIRMED`, `WAITING`. `CANCELLED`는 FR-06에서 추가한다.
- `CourseSession`(course 패키지)은 바꾸지 않는다. 확정 수는 컬럼으로 두지 않고 매번 집계한다. 같은 회차의 신청은 아래 락으로 직렬화되므로 집계값이 정확하다.

## 4. 트랜잭션과 동시성

### 처리 순서 (`EnrollmentCommandService.enroll(Long sessionId, Long employeeId)`, `@Transactional` 하나)
1. **회차 락:** `courseSessionRepository.findByIdForUpdate(sessionId)` → `SELECT ... FOR UPDATE`. 없으면 404 `SESSION_NOT_FOUND`
2. **종료 확인:** `session.isClosed()`이면 409 `SESSION_CLOSED`
3. **중복 확인:** `enrollmentRepository.existsBySessionIdAndEmployeeId(sessionId, employeeId)`가 참이면 409 `ENROLLMENT_DUPLICATE`
   - `CANCELLED`가 아직 enum에 없으므로 상태 조건 없이 확인한다. FR-06에서 취소를 넣을 때 "취소 제외" 조건으로 바꾼다.
4. **확정 수:** `enrollmentRepository.countBySessionIdAndStatus(sessionId, CONFIRMED)`
5. **판정:** `확정 수 < capacity`이면 `CONFIRMED`. 아니면 `countBySessionIdAndStatus(sessionId, WAITING) < capacity / 2`일 때 `WAITING`. 둘 다 아니면 409 `SESSION_FULL`
6. **저장:** `enrollmentRepository.saveAndFlush(...)`. 유일 인덱스 위반(`DataIntegrityViolationException`)은 409 `ENROLLMENT_DUPLICATE`로 바꾼다. 다른 무결성 위반은 그대로 던진다.
   - 판정은 `EnrollmentConstraints.isActiveUniqueViolation`이 한다. 먼저 Hibernate가 준 제약 이름이 `ux_enrollment_session_employee_active`인지 본다. 이름이 없으면 SQLState `23505`인지 본다.
   - SQLState를 함께 보는 이유: Hibernate는 제약 이름을 PG 오류 메시지 문자열에서 잘라 낸다. 그래서 PG 메시지 언어(`lc_messages`)가 한국어면 이름이 비어 있을 수 있다. `enrollment`의 유일 제약은 PK(IDENTITY 자동 생성)와 이 인덱스뿐이므로, 23505는 이 인덱스 위반이다.
7. **응답:** `EnrollmentResponse.from(enrollment)`를 트랜잭션 안에서 만든다.
8. **커밋:** 커밋할 때 회차 행 락이 풀린다.

### 락 대상과 이유
- **락 대상:** `course_session`의 해당 회차 행 하나 (`@Lock(LockModeType.PESSIMISTIC_WRITE)`)
- **이유:** 아직 없는 `enrollment` 행에는 락을 걸 수 없다. 같은 회차에 대한 신청을 회차 행 락으로 한 줄로 세우면, 1~6단계 사이에 다른 트랜잭션이 끼어들 수 없다. 그래서 확정 수가 정원을 넘지 않는다.
- **같은 트랜잭션:** 락 조회, 확정 수 확인, 저장이 모두 `enroll()`의 한 트랜잭션 안에 있어야 한다. 락을 나중 단계로 옮기거나 트랜잭션을 나누면 보장이 깨진다.
- **중복 방지 이중화:** 같은 임직원의 동시 요청도 회차 락으로 직렬화되어 3단계에서 걸러진다. 부분 유일 인덱스는 락을 거치지 않는 경로(향후 관리자 일괄 등록 등)까지 막는 최종 보장이다.
- **영향:** 같은 회차의 신청끼리만 기다린다. 다른 회차 신청은 서로 막지 않는다. 회차 수정·종료(FR-03)는 지금 락 없이 조회한다. 그래서 신청과의 순서가 보장되지 않고, 정원을 확정 수보다 작게 줄이는 것도 막지 않는다. FR-03 후속 이슈로 남긴다(최종 검토 경고 3).
- **락 대기 시간:** 별도 타임아웃을 두지 않는다. 트랜잭션이 짧아 대기도 짧다. 운영에서 문제가 되면 `lock_timeout`을 검토한다.
- **H2 한계:** H2의 락 동작은 PostgreSQL과 다르다. 그래서 락·유일 인덱스·동시성 검증은 모두 pgtest(로컬 PostgreSQL `eduhub_test`)에서 한다.

동시성 테스트 방식
- 서비스 `enroll()`을 직접 부른다. 스레드 풀 32개, `CountDownLatch`로 동시에 출발시키고, 모두 끝날 때까지 기다린다.
- 테스트 클래스에는 `@Transactional`을 붙이지 않는다(각 신청이 자기 트랜잭션으로 커밋되어야 함). 데이터는 `@AfterEach`에서 지운다.
- 검증: DB의 `CONFIRMED == 10`, `WAITING == 5`, 전체 15건. 스레드 결과에서 성공 15, `SessionFullException` 85, 그 밖의 예외 0.
- `@Lock`을 주석 처리하면 확정이나 대기가 상한을 넘어 실패해야 한다. 이 확인은 개발자가 직접 실행한다.
- 작업 지시의 원래 기대값은 "확정 10, 대기 90"이었다. 개발자가 D-02를 지금 적용하기로 정해(Q1) 위 값으로 바꿨다.
